# Thermo-nuclear code-quality review — 2026-09-04

## Вердикт

Ветка уже значительно сильнее обычного MVP: границы sealed evidence, host-owned decisions, immutable receipts, sandbox и provenance реализованы всерьёз, а не как декларации. Текущий change-set также проходит типизацию и весь quick-набор. Но автопоиск пока нельзя считать надёжным продуктовым циклом: один отказ автора обрывает остальные гипотезы, цена автора отсутствует в оценке перед подтверждением, а варианты выбираются на том же development-наборе, из которого получили диагноз. Есть ещё два заметных разрыва доверия на входе и в evidence: shell-подобная команда разбирается простым `split`, а agent-reported tool notes продолжают увеличивать число «tool calls».

Approval bar этого review не пройден. Ниже только findings с воспроизводимым эффектом; косметические замечания опущены.

## Findings

### P1 — один `no-change` обрывает multi-hypothesis search и выбрасывает уже готовые варианты

**Где:** `src/application/improvement-loop.ts:1107-1133`, затем `:1164-1177`.

Цикл обещает сравнить 2–4 изменения, но первый авторский ответ `no-change` делает `break`. Если variant 1 подготовил валидный proposal, variant 2 вернул `no-change`, а variant 3 мог бы подготовить другой proposal, третий вообще не будет вызван. Для `candidates > 1` единственный уже готовый proposal затем маркируется `too-few-hypotheses`, и весь поиск заканчивается без проверки. Локальная неудача одного автора тем самым отменяет независимые попытки и уже оплаченный результат.

**Code-judo:** вынести сбор вариантов в маленький `collectProposalVariants` с результатом `{ proposals, attempts, refusals }`. `no-change` должен относиться только к своему варианту; продолжать до исчерпания запрошенного числа. Останавливать цикл лишь когда proposals пуст либо после всех попыток всё ещё меньше `MIN_SEARCH_CANDIDATES`. Это удалит неявное значение `exhaustedAuthor`, которое сейчас одновременно означает отказ одного варианта и отказ всего автора.

**Тест:** сценарий `propose → no-change → propose` при `candidates: 3` обязан передать два proposal в `runProposalSearch`; сценарий из трёх `no-change` обязан остановиться с агрегированным bounded reason и тремя receipts.

### P1 — окно подтверждения показывает только цену Target, хотя внутри него запускается отдельный платный Builder

**Где:** `src/workbench/decisions/improve.ts:43-92`; лимиты автора — `src/application/improvement-author.ts:19-25, 133-164, 345-364`.

`plannedExecutions` и `host.runEstimate(...)` считают только Target executions. После этого диалог разрешает до `maxCycles × candidates × 8` отдельных Builder requests, каждый с контекстом до 96 KiB и output до 2,048 tokens. Текст сообщает, что расход «additional», но не даёт ни оценки, ни верхней границы в деньгах. Для продукта, который делает одно money confirmation на цикл, это не мелочь интерфейса: человек подтверждает конкретную сумму/время, а существенный второй счёт находится за её пределами.

**Code-judo:** один `ImprovementBudget` должен владеть Target и authoring spend. `prepareImprovementAuthor` может вернуть model pricing и детерминированный верхний token/request bound; `plannedImprovementCost` складывает обе части и кладёт их в один subject/receipt (`target`, `builder`, `total`, отдельно unknown). Если цену Builder нельзя определить, confirmation должен явно показывать `total: unknown`, а не точную оценку Target как оценку операции.

**Тест:** при `maxCycles: 2, candidates: 3` subject содержит 48 max author requests и отдельную стоимость; неизвестная цена автора делает общий cost unknown; recorded-only author сохраняет нулевой authoring spend.

### P1 product — поиск оптимизирует и выбирает гипотезы на тех же кейсах, которые породили диагноз

**Где:** `src/application/improvement-loop.ts:1073-1127, 1179-1197, 1282-1349`; это же честно отмечено в `docs/ROADMAP.md` Stage 3.

Автор получает failure mode из development EvalRun, затем cheap check и full verification снова используют `developmentCorpus`. При 2–4 вариантах selection pressure становится заметным: frontier выбирает вариант, лучше всего подогнавшийся к уже прочитанным ошибкам. Sealed exam запускается позже, при ship, и способен только отклонить уже выбранный кандидат; он не даёт unbiased сигнала для выбора. Поэтому основной продуктовый тезис «лучшее изменение» пока означает «лучшее на прочитанном наборе».

**Code-judo:** сделать `EvaluationPartition` канонической входной моделью цикла: `authoring/diagnosis`, `validation`, `sealed`. Автор видит только diagnosis split; screen и frontier работают по validation split; sealed запускается один раз для выбранного человеком кандидата. Один тип/receipt должен не позволять случайно передать development corpus в validation lane.

**Тест:** sentinel из validation case не попадает в author prompt/failure bundle; ranking меняется только от validation results; sealed side never reads before ship; одинаковый corpus id в diagnosis и validation отклоняется до model spend.

### P1 — onboarding показывает argv с кавычками, но введённую команду разбирает по пробелам

**Где:** `src/builder/onboarding.ts:438-440, 470-485`.

Review отображает argv через `JSON.stringify`, то есть обещает корректные границы аргументов. Но строка оператора проходит через `text.trim().split(/\s+/)`. Команда `python3 agent.py --prompt "prompts/system prompt.md"` попадёт в manifest как пять аргументов с буквальными половинами кавычек. То же произойдёт с пробелом в пути, escaped quote и аргументом с JSON. Adoption успешно коммитит конфигурацию, которая не запускает реального агента.

**Code-judo:** использовать маленький parser только для argv quoting (`'...'`, `"..."`, backslash), без shell expansion, substitutions и globbing. Ещё проще и безопаснее — хранить/editировать массив аргументов в host-owned UI, а строку использовать лишь как presentation. Неразборчивую строку нужно вернуть в тот же review с конкретной ошибкой, ничего не записывая.

**Тест:** quoted path, empty argument, escaped quote/backslash; незакрытая кавычка не вызывает `wrap-target`; round-trip `renderArgv(parseArgv(text))` сохраняет каждый аргумент.

### P2 — `tool_note` помечен как неподтверждённый в trace, но всё ещё увеличивает подтверждённую метрику `toolCalls`

**Где:** `src/target/session-command.ts:355-375, 378-420`; потребители — `src/builder/render/trace.ts:108,237`, `src/evidence/pages.ts:264,544`, `src/report.ts:714`.

Новый `evidence: "reported"` правильно не позволяет self-report пройти grader `tool_called`. Но `note()` всё равно делает `this.toolCalls += 1`, а downstream показывает это число как «Tool calls» без квалификации. Агент может выпустить 20 notes, не выполнить ни одного инструмента, провалить grader и одновременно выглядеть в таблице как агент с 20 вызовами. Detailed trace объяснит расхождение, сводки и отчёты — нет.

**Code-judo:** модель активности должна иметь два числа: `executedToolCalls` и `reportedToolCalls`; legacy `toolCalls` либо оставить alias только для executed, либо мигрировать schema один раз. Per-turn safety budget может считать оба как `protocolActions`, но продуктовые evidence и cost views должны считать host-observed executions.

**Тест:** run с двумя `tool_note` и одним brokered call пишет `executed=1, reported=2`; grader и все summary projections показывают 1 executed и явно 2 reported; legacy Pi run остаётся без изменения presentation.

### P2 — export молча выпускает неполную training line, если immutable corpus больше не читается

**Где:** `src/application/export-dataset.ts:808-816, 865+`; `corpusTaskLookup` в конце того же файла намеренно превращает любую ошибку в пустой `Map`.

Для published-corpus eval `world.initial` и simulated-user goal берутся не из RunRecord, а повторно из corpus store. Если store повреждён, отсутствует или не проходит hash verification, lookup глотает исключение, а export продолжает писать conversation с final world, но без initial world/persona/goal. Это уже другой обучающий пример, при этом summary считает его успешно exported. README обещает world before/after и simulated user's turns, а текущий файл не сообщает, что контекст потерян.

**Code-judo:** вернуть из lookup discriminated result: `manifest-no-task-facts | corpus-facts | corpus-unreadable`. Последнее должно давать infra skip для всех affected members с одной bounded note. Ещё лучше — pin task projection рядом с EvalRun в момент выполнения; тогда export вообще не перечитывает mutable availability store.

**Тест:** удалить/испортить опубликованный corpus после eval и убедиться, что lines=0, `skipped.infra === memberCount`, note называет недоступный dataset hash; manifest-dataset legacy run по-прежнему экспортируется без выдуманного world.

### P2 structural — центральный Workbench остаётся 3,405-строчным god object, поэтому каждая функция продукта разрастается сразу в нескольких слоях

**Где:** `src/workbench/workbench.ts:833-3397` (класс), особенно `viewOf` `:2771-2938`, `submit` `:2940-3259`, dispatcher `:3271-3395`; рядом `src/i18n.ts` — 3,077 строк, `src/application/tool-workshop.ts` — 2,920, `src/eval.ts` — 2,262.

Решения уже частично вынесены в `workbench/decisions/*`, но класс всё ещё одновременно собирает inventory, строит projections, управляет workshop/grants, принимает drafts, оценивает spend и диспетчеризует state machine. Новый improvement author потребовал протянуть dependency через extension → workbench → decision host; следующий validation split снова затронет тот же узел. Это не просто большой файл: список imports и число смысловых владельцев делают product changes связанными и увеличивают вероятность различий между CLI, Builder и serve.

**Code-judo:** оставить `AhdeWorkbench` фасадом из пяти методов и вынести владельцев: `WorkbenchReader` (`view`, projections), `SubmissionService`, `WorkshopSession`, `DecisionRouter`, `EstimateService`. Router — typed map по `DecisionInput["kind"]`, а не 24 `if`; текущие `decisions/*` уже почти готовы стать значениями карты. `i18n.ts` разделить механически на locale data files и formatter — это отдельный безопасный commit, не prerequisite для цикла.

**Тест:** contract tests на одинаковую projection/decision semantics через facade; compile-time exhaustive router test; существующие workbench integration tests должны пройти без переписывания assertions.

### P3 structural — structured redaction использует строковый «credential-probe» и может схлопнуть разные ключи

**Где:** `src/application/export-dataset.ts:297-319`.

Чтобы определить, является ли key чувствительным, код собирает псевдостроку `${key}: "credential-probe"` и ищет, вставил ли regex-redactor `[REDACTED]`. Одновременно сам key проходит `boundedText`, поэтому два длинных ключа с общим префиксом превращаются в один property в `Object.fromEntries`; один value молча исчезает. Это magic abstraction на evidence boundary: поведение structured data зависит от формата поддельной строки и случайных regex деталей.

**Code-judo:** экспортировать из `trace.ts` явный `isSensitiveFieldName(name)` и использовать общий рекурсивный `redactStructured(value, limits)`, который возвращает `{ value, truncated }`. Не обрезать object keys по отдельности; мир уже ограничен 16 KiB, а oversized judge structure следует целиком помечать truncated/skip, а не менять его topology.

**Тест:** nested secret object, camelCase/custom token keys, два ключа длиннее `MAX_DATASET_NAME_CHARS` с одинаковым prefix, reserved-looking benign value; ни один non-secret sibling не исчезает.

## Bounded scope, который стоит реализовать сейчас

1. Исправить multi-variant collection (`no-change` не делает `break`) и покрыть смешанный результат тестом.
2. Заменить whitespace split в adoption на безопасный argv parser/round-trip tests.
3. Разделить executed и reported tool activity во всём evidence projection; не менять protocol wire.
4. Сделать corpus resolution в export fail-closed и не выпускать неполные published-corpus lines.
5. В confirmation автопоиска показывать общий budget: Target + Builder; unknown остаётся unknown.

Это один связный reliability slice: пользователь видит корректную команду и цену, поиск действительно пробует заказанные варианты, а evidence после прогона не преувеличивает действия и не теряет исходный контекст. Validation split — следующий отдельный product slice; он меняет экспериментальный контракт и заслуживает собственную миграцию/acceptance run. Декомпозицию Workbench делать после этих исправлений механическим refactor без изменения поведения.
