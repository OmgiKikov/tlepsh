# AHDE: комплексная оценка продукта и следующий сильный релиз

Дата: 5 сентября 2026. Проверенная ревизия: `78690e5`, ветка `codex/product-wow`.

## Вывод

AHDE — работающая среда улучшения агентов с серьёзным отношением к доказательствам. Она связывает реальное исполнение, диагноз, ограниченную правку, независимое сравнение, закрытый экзамен и решение человека. Самая ценная часть проекта уже существует.

Следующий скачок качества даст цельный пользовательский путь: подключить существующего агента, показать конкретный промах, увидеть изменение поведения рядом с исходным, понять ограничения измерения и выпустить версию по собственным критериям. Для этого важнее интеграция, понятность и доверие к результату, чем увеличение числа возможностей.

Моя субъективная оценка текущего состояния: **7/10 как продукт для технического раннего пользователя**. Инженерный фундамент — около 8/10, понятность первого знакомства — около 6/10, готовность к широкому самостоятельному распространению — около 5/10. Это экспертное впечатление по указанным ниже критериям, а не результат пользовательского исследования.

Сильнейший первый сегмент — владельцы Python support/RAG-агентов с базой знаний, состоянием клиента и инструментами. Именно здесь существующие `world`, tool broker, command Target, KB, incident import и independent validation складываются в полезный продукт.

## Конкретные дефекты, которые стоит исправить до распространения

### 1. P1: promotion guard теряет состояние мира и сценарий диалога

В [regression-guards.ts:134](../../src/application/regression-guards.ts) `guardCaseFor` копирует `input`, `expected`, `messages`, `metadata`, `graders`, но не `world` и `simulatedUser` (строки 144–150).

Следствие: кейс «клиент с таким состоянием должен получить такое действие» становится другим тестом. Вместе с `world` исчезают и условия конечного состояния, если они заданы через `world.expect`. Многоходовая проверка может превратиться в одиночный запрос. Это особенно существенно для главного support-сценария AHDE.

В узком воспроизведении объект с обоими полями после `guardCaseFor` не содержит ни одного из них. Нужна lossless-проекция семантики кейса и проверка пути «stateful/simulated case → promotion → guard draft → следующая публикация». Существующие тесты guards этот случай не закрывают.

### 2. P1: watch может показать healthy при недостоверном измерении

В [watch.ts:327](../../src/application/watch.ts) отдельно обрабатывается `comparison.status === "invalid"`, но `inconclusive` из-за инфраструктурных ошибок лишь добавляет note. Затем статус берётся из gate verdict (строки 337–345); `inconclusive` превращается в `healthy`. `watchExitCode` возвращает для healthy код 0 (строки 371–375).

Это смешивает две разные ситуации: сравнение достаточно надёжно и не обнаружило изменений; сравнение не состоялось из-за ошибок. При подстановке результата с 20 инфраструктурно ошибочными задачами фактическая функция вернула `status: healthy`, `exit: 0`.

Нужно отдельное состояние `measurement-unavailable` либо существующее `not-comparable`, с ненулевым exit code. Здоровье сервиса и статистическое отсутствие drift должны выводиться только из пригодного измерения. Дополнить тестом полного monitor-пути с недоступным mock endpoint.

### 3. P1: неизвестный расход может стать известным отношением цен

[compare.ts:176](../../src/compare.ts) агрегирует `(runCost(record) ?? 0)` и аналогично сводит отсутствующие tokens к нулю. Сами `runCost/runTokens` правильно возвращают `null`; ошибка появляется при агрегировании.

Пример воспроизведения: стоимость Target в baseline неизвестна, judge стоил $0.10; candidate Target $0.90, judge $0.10. Результат — `costRatio: 10`, хотя полная стоимость baseline неизвестна. Если расход всех Target неизвестен, известные judge-subtotals всё равно могут создать правдоподобный ratio.

Нужно сохранять полноту измерения в ResourceTotals: known subtotal, число неизвестных запусков и nullable total/ratio. Ноль допустим только для доказанного нулевого расхода. Особенно важно сделать это до оптимизации моделей по цене.

### 4. P2: опубликованный пример Python starter не работает вне checkout

[README.md:360](../../README.md) предлагает `ahde init my-agent --template templates/python-agent`. [cli.ts:832](../../src/cli.ts) трактует `--template` как путь относительно текущей папки. В новой временной папке реальный CLI завершился с кодом 2 и ENOENT для `templates/python-agent/manifest.yaml`.

Кроме того, обычный `ahde init` и bootstrap пустой папки выбирают `basic-agent`, хотя Python назван основным starter. Предлагаемая форма: встроенные имена `--template python-support` и `--template pi-basic`, плюс отдельная поддержка пути к пользовательскому шаблону. Проверять из произвольного cwd после установки tarball.

### 5. P2: vendor source нельзя штатно восстановить через submodule

`vendor/pi-mono` отслеживается git как gitlink на `5cd6a2a`, но `.gitmodules` отсутствует. Реальный `git submodule status` завершился с кодом 128: `no submodule mapping found in .gitmodules for path 'vendor/pi-mono'`.

Обычный потребитель пользуется tarballs и может не встретить проблему. Новый контрибьютор, которому нужно пересобрать закреплённый runtime с patch, встретит её сразу. Нужен корректный submodule mapping либо явный source-fetch/rebuild script с pinned revision и проверкой patch. См. [vendor/patches/README.md](../../vendor/patches/README.md).

## Самая важная продуктовая граница: улучшение и готовность к работе

Текущий sealed gate сознательно работает как относительный guardrail: ниже минимума данных — underpowered; доказана регрессия — fail; иначе pass. Cost, latency и отдельные ухудшившиеся кейсы сами по себе не блокируют выпуск. Это явно описано в [comparison-gate.ts:19](../../src/domain/comparison-gate.ts), а не случайная ошибка реализации статистики.

В [live acceptance](2026-09-05-live-improvement-acceptance.md) одна выпущенная версия имела 7/30 полностью успешных запусков закрытого экзамена — 23.3%. Другая имела 21/30. Проект это честно объясняет. Но пользователь легко прочитает «экзамен пройден» как «агент достаточно хорош».

Нужны три отдельных ответа:

- **Изменение:** лучше / хуже / недостаточно данных относительно baseline.
- **Пригодность:** достигнуты ли заданные владельцем критерии работы.
- **Достоверность:** достаточно ли данных и надёжен ли измеритель для этого вывода.

Предлагаемый следующий объект — версионированные **условия выпуска**: критические сценарии, минимальное качество по задачам, допустимые расходы/задержка, требования к полноте данных и калибровке judge. Значения задаются владельцем, привязываются к эксперименту до проверки и применяются одинаково в Builder, CLI, serve и passport. Произвольные универсальные пороги вроде «всем 95%» здесь не нужны.

Имеющиеся Spec successCriteria, calibration policy и promotion guard drafts дают часть основы, но не заменяют такой контракт. Подсказку «хуже не доказано» также нужно одинаково выводить в Evidence compare: сейчас [pages.ts:703](../../src/evidence/pages.ts) всё ещё показывает `Sealed verdict: pass`, тогда как release card уже объясняет смысл подробнее.

Отдельный пример границы измерителя: `cites_source` допускает ID источника или lexical overlap. В бесплатном демо неправильный ответ про 7 дней получает положительную проверку источника при политике 30 дней. Это допустимо для проверки пересечения/цитирования, но не доказывает верность факта. Для чисел, дат, денежных сумм и действий нужны отдельные assertions; semantic faithfulness также следует измерять и калибровать отдельно. RAG X-ray уже честно предупреждает об этой границе — сохранить эту честность в итоговых выводах.

## Как сделать продукт значительно удобнее

### Первый запуск: показать пользу до сложной настройки

Сейчас install path начинается с `git clone <this repository>`, сборки и link. Бесплатный demo расположен почти в конце README. Пользователь ещё не увидел результата, но уже должен разобраться в Node/Git, моделях Builder/Target/judge, ключах и терминологии.

Предлагаемый первый экран:

> **Улучшить моего агента** — выбрать папку и один неудачный диалог.
>
> **Посмотреть пример** — без ключей и платных запросов пройти готовый случай за несколько минут.

Демо должно закончиться тем же экраном сравнения, что и реальная работа, и понятным переходом к своему агенту. Для реальной настройки — рекомендованные сочетания ролей с объяснением компромисса и полной оценкой расходов; технические model IDs доступны в подробностях.

Это можно сделать в текущем Builder. Для распространения нужен один копируемый install path: версионированный tarball из release tag с checksum, затем при готовности registry install. Сначала воспроизводимая доставка, потом упрощение команды.

### Подключение папки: доказать совместимость до большой проверки

Распознавание Python-папки не равно адаптации произвольного Python-агента. [agent-folder-detect.ts:189](../../src/application/agent-folder-detect.ts) находит обычные entry filenames; [target-scaffold.ts:368](../../src/application/target-scaffold.ts) добавляет manifest/evals/AGENTS, а затем объявляет protocol v1. Код адаптера при этом не создаётся.

Нужен короткий integration check: точная команда → handshake → один запрос → завершённый ответ → доступные инструменты/ограничения. Для одного-двух поддерживаемых patterns Python function/HTTP endpoint можно подготовить небольшой adapter diff. Несовместимость должна объясняться до расходов на полноценный eval. Поддержку всех фреймворков одновременно обещать рано.

### Главный экран решения: конкретный случай «до → после»

Паспорт уже имеет хорошую визуальную иерархию. Trace explorer пока устроен для разработчика движка: сырые run IDs, «повтор 0», технические grader names, смешанный RU/EN и много чисел до самого диалога. Текущее сравнение даёт таблицу и ссылки на отдельные baseline/candidate runs ([pages.ts:674](../../src/evidence/pages.ts)).

Нужна одна предметная сцена принятия решения:

1. Заголовок: «Исправлено неверное действие при заблокированном счёте».
2. Слева исходный ответ и реальные действия, справа новый вариант.
3. Выделено изменившееся состояние мира, вызов инструмента или подтверждённый факт.
4. Рядом короткая причина изменения и раскрываемый diff.
5. Видны независимый результат, оставшиеся ошибки, стоимость и условия допуска.
6. Один следующий выбор: принять проверенную версию, продолжить улучшение либо отклонить.

Начинать следует с наиболее существенного исправленного кейса и наиболее существенной регрессии. Хеши и полный trace остаются в подробностях. RU/EN надо последовательно применять ко всей странице, включая headers, grader explanations и пустые состояния.

Полноценный управляющий UI внутри AHDE сейчас является явным non-goal. Поэтому есть два честных варианта: улучшить read-only Evidence и оставить управление в Builder; либо осознанно добавить тонкий companion над `serve`. Второй вариант — продуктовое решение, а не обязательный переписанный frontend.

### Повторное использование: очередь реальных ошибок

Feedback, imports, watch, regression drafts и version history уже есть. Пользовательская ценность вырастет, если связывать их через один видимый инцидент:

> «Эта жалоба воспроизведена на версии X; проверены две гипотезы; выбранная правка исправила действие; вот независимая проверка; защита от повторения включена в следующую корзину».

Первые состояния: новый → воспроизведён → исправление проверяется → готов к решению → выпущен / отклонён. Состояние выводится из durable refs; после restart всё восстанавливается. Начать можно с уже работающего `imports/`, без нового production proxy и десятка интеграций.

### Большой следующий шаг: повтор одного случая с контролируемым изменением

После исправления измерения расходов можно дать эксперимент «тот же диалог и мир, другой prompt/model/retrieval». Важно показывать, какая ось изменена, какие условия сохранены, что стоит проверка и можно ли результаты сравнивать. Продукт отвечает на конкретные вопросы: «маленькая модель уже справится?», «помогла новая база знаний?», «за что я плачу задержкой?».

Сначала ограниченный ручной replay и понятное сравнение; поиск по большому числу моделей и параметров стоит добавлять по реальному спросу. Independent validation и закрытый экзамен сохраняются.

- **Узкий runtime для decision families.** Сейчас [decisions/shared.ts:6](../../src/workbench/decisions/shared.ts) определяет `DecisionHost = AhdeWorkbench`; вынесенные handlers всё ещё зависят от целого класса. По мере изменения решений дать им небольшой контекст операций/receipts/gate. Не дробить 3 519 строк Workbench механически: уменьшать знания одного модуля о другом.
- **Одна политика следующего шага.** Согласовать stage derivation, legal actions, blocker priority и пользовательскую фразу. Источники сейчас распределены между inventory, next-actions, transition-policy и render. Новый UI не должен снова вычислять workflow самостоятельно.
- **Измерить скорость до введения хранилища/кэша.** Проверить p50/p95 `view/status` на 10, 100 и 1 000 Eval Runs, отдельно с большим corpus/candidate history. Пока количественной претензии к производительности нет; рекомендация — получить baseline перед оптимизацией.
- **Контракт API для companion.** `serve` держит операции в памяти и удаляет при завершении; event replay ограничен текущим процессом. Перед богатыми UI нужны получение результата операции и определённые retry/idempotency semantics. Восстановление через `/view` полезно, но не равно журналу конкретного запроса. Сначала маленький поддерживаемый client/example, а не расширение публичного экспорта всех internals.
- **Linux как проверенное обещание.** Текущий CI только macOS; Linux/bwrap и реальный Docker должны иметь отдельный тестовый контур, если платформа заявляется пользователям. Пропущенные Docker-тесты нельзя считать подтверждением контейнерного исполнения.
- **Документация как один текущий контракт.** ROADMAP ещё говорит о Pi-only и будущем autoloop; README уже описывает Python и реальный author path. ROADMAP обещает непатченный runtime, vendor docs описывают patch. Датированные ревью оставить историей, текущий roadmap переписать по фактическому состоянию.

## Очерёдность следующего релиза

| Порядок | Законченный результат | Проверяемый критерий выхода |
|---|---|---|
| 1. Доверие | Исправлены world/simulated guards, watch, неизвестная стоимость | Stateful regression сохраняет смысл; outage не даёт healthy; unknown не даёт числовой cost ratio |
| 2. Доставка | Каноническая ветка, воспроизводимый vendor, release tarball, правильные шаблоны | Установка в чистой среде и Python starter из любого cwd; поддерживаемые OS проходят gate |
| 3. Подключение | Узкий, но настоящий integration check и adapter path | Несколько незнакомых Python support-агентов проходят до первого исполнения без ручной правки протокола |
| 4. Решение | Поведение до/после, условия выпуска, единая формулировка evidence | Человек объясняет, что исправлено, что осталось и почему допустим выпуск, не читая run IDs |
| 5. Повторение | Инцидент связывает импорт, гипотезу, проверку и выпуск | Через неделю и после restart пользователь находит текущую работу за минуту |
| 6. Эксперименты | Контролируемый replay по prompt/model/retrieval | Сравнимые результаты с корректной полной стоимостью и независимым подтверждением |

Для пунктов 3–4 провести минимум пять сессий с независимыми незнакомыми пользователями и агентами, которых автор AHDE заранее не готовил. Измерять time-to-first-diagnosis, time-to-reviewable-candidate, число ручных вмешательств, непонятных вопросов и незавершённых сессий. Ориентир для гипотезы: первый полезный диагноз ≤10 минут, проверяемый кандидат ≤20 минут. Эти цели ещё не доказаны и зависят от размера eval и скорости моделей.

Главная метрика: доля подключений реального support-агента, завершившихся независимо проверенным полезным исправлением за одну сессию без внешнего ручного ремонта. Дополнительно — возвращаются ли пользователи с новым инцидентом через неделю. Это лучше проверяет ценность, чем число команд, тестов или поддерживаемых моделей.
