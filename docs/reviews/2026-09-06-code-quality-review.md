## Подтверждённые findings

### Q1 · P1 · Ошибка чтения sealed metadata превращается в разрешение

`sealedDatasetHashesFor` в [export-dataset.ts](../../src/application/export-dataset.ts) (1047), `sealedCorpusHashes` в [label-session.ts](../../src/builder/label-session.ts) (98) и [cli.ts](../../src/cli.ts) (540) копируют одно правило и возвращают пустой Set при **любой** ошибке `listCorpora`. При этом [corpus.ts](../../src/corpus.ts) (423) уже возвращает пустой список для отсутствующего каталога. Перехват нужен не для пустого проекта: он скрывает повреждённый metadata, небезопасный путь или недоступное хранилище.

Для старого EvalRun без `evidenceVisibility` и префикса `sealed-` этот набор — единственный признак sealed происхождения, который проверяет `isSealedEvalRun` (`eval.ts:1429`). Если набор потерян, защита работает по ложной предпосылке. В `builder-proposal.ts:1168` такое же чтение уже распространяет ошибку; разные поверхности применяют разную политику к одному хранилищу.

**Проверено запуском:** временный `stateRoot`, который является обычным файлом, вызывает отказ `listCorpora`, но `sealedDatasetHashesFor` возвращает пустой Set; `isSealedEvalRun` для legacy записи затем возвращает false. Вывод: `{"corpusReaderRejected":true,"guardReturnedHashCount":0,"legacyRunIsSealed":false}`. Это проверка предпосылки обхода, не утверждение, что в пользовательских данных произошла утечка.

**Минимальное исправление:** один metadata-only helper в существующем `corpus.ts`; отсутствие каталога остаётся пустым результатом, ошибки распространяются. Заменить копии и проверить другие callers того же правила. Не читать sealed task content для классификации.

**Приёмка:** пустое новое хранилище работает; повреждённый metadata запрещает export/label до чтения trace; legacy sealed hash не проходит; обычный development corpus проходит. Проверить CLI и TUI callers, а не только helper.

### Q2 · P2 · Два импортера владеют одной и той же безопасностью чтения

[builder-corpus-import.ts](../../src/application/builder-corpus-import.ts) (100–202) и [dataset-source.ts](../../src/application/dataset-source.ts) (96–197) отдельно реализуют containment, проверку каждого компонента, stable inode, ограничение байтов, чтение блоками, UTF-8 и хеширование. Различие реальное, но небольшое: native JSONL importer имеет свой меньший лимит и после чтения валидирует задачи; raw dataset source поддерживает несколько форматов.

Дублирование опаснее лишних строк: исправление файловой гонки или защиты пути приходится помнить в двух местах. Уже есть локальное расхождение с reader в `candidate-artifacts.ts`: тот использует `O_NONBLOCK`, чтобы подмена файла FIFO между `lstat` и `open` не остановила процесс, а оба импортера этого не делают. FIFO-гонка здесь установлена чтением кода; конкурентный exploit не воспроизводился.

**Минимальное исправление:** переиспользовать существующий `readDatasetSource` для чтения inbox, добавив только реально различающийся byte limit. Native importer сохраняет свой более строгий path schema и парсинг `CorpusTaskSchema`, но перестаёт владеть вторым filesystem reader. Если полное переиспользование требует ослабить path policy, выделить только общий физический read внутри этих двух модулей; не создавать общий storage framework.

**Приёмка:** прежние отдельные лимиты, byte hash, запрет symlink/private roots, отказ при изменении inode и невалидном UTF-8 сохранены. Native дубликаты id и ошибки строк всё ещё обрабатывает importer. Добавить одну проверку, что FIFO не блокирует чтение.

### Q3 · P2 · Четыре readers копируют каталог кандидатов

Одинаковые `candidateIds` находятся в [agent-log.ts](../../src/application/agent-log.ts) (163), [experiment-history.ts](../../src/application/experiment-history.ts) (129), [version-passport.ts](../../src/application/version-passport.ts) (96), [watch.ts](../../src/application/watch.ts) (204). Все строят один путь, читают только директории, исключают symlink, сортируют и скрывают ошибки листинга. Это один storage read, а не четыре доменные операции.

**Минимальное исправление:** одна exported функция в существующем `candidate-artifacts.ts`; callers сохраняют собственные правила чтения и проверки CandidateRecord. Никакого repository interface, кэша или нового класса. Косметическую политику пустого каталога не менять незаметно одновременно с переносом.

**Приёмка:** отсутствие кандидатов, порядок, отбрасывание symlink и чтение исторического кандидата работают как прежде; существующие тесты history/passport/watch/log остаются зелёными. Число копий — одна.

### Q4 · P2 · В репозитории остаётся второй, устаревший «реальный цикл»

[scripts/real-loop.mjs](../../scripts/real-loop.mjs) импортирует внутренние application functions, подставляет diff между двумя заранее известными SHA (160–162), задаёт human actor `kikov`, затем сам делает review, promotion и adoption (217–221). Это исторический August replay, а не проверка того, что сегодняшний пользователь проходит публичный продуктовый flow и Builder действительно придумывает улучшение.

Проблема — лишняя исполняемая версия жизненного цикла, которую можно принять за актуальную приёмку. В `package.json` уже есть отдельные `acceptance:live`, `acceptance:python-live`, `acceptance:guided` и `verify:package`; данный файл не подключён к ним. Его результат не должен подтверждать удобство текущего продукта.

**Минимальное исправление:** удалить устаревший скрипт. Исторический код остаётся в Git; исторический результат, если нужен, описывается как replay. Не заменять его ещё одним orchestration API.

**Приёмка:** нет рабочих callers удалённого скрипта; сохранённые публичные acceptance команды и package verification проходят; свежий native flow проверяется отдельно без подстановки известного diff.

## Что проверено и не требует новой работы

- Изменённые `.ts` файлы не пересекли порог 1000 строк снизу. Уже крупные `workbench.ts`, `eval.ts`, `manifest.ts` заслуживают внимания при изменении их обязанностей, но механическая раскладка по файлам не уменьшит число правил.

Тест `npx vitest run tests/export-dataset.test.ts -t 'reports an eval run index'` прошёл: **1 passed, 53 skipped**. Лог: `.ahde/quality-export-index-check.log`. Merge/cherry-pick старой реализации не нужен.
- Python function bridge не создаёт второй agent runtime: он адаптирует существующую функцию к wire protocol, не сочиняет tool/usage events. Не предлагать обобщённый plugin layer поверх него.
- Ревью структуры само по себе не доказывает «последнее слово техники», UX или качество модели. Для этих утверждений нужны проверенный пользовательский flow и отдельная проверка актуальных первичных источников.

4. Пройти публичный newcomer → run → trace → improvement flow; отдельно проверить исторический replay после evaluator bump.
5. Общий typecheck/tests, package verification и CI на опубликованном SHA. Измерять фактическое сокращение после правок, не обещать его заранее.
